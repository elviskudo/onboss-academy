Ada duapendekatan utama: backup logical (`pg_dump`) dan backup fisik (`pg_basebackup`). Keduanya punya tempat masing-masing.

## Backup Logical

```bash
pg_dump -U postgres -Fc academy > academy.dump
pg_dump -U postgres -Ft academy > academy.tar
pg_dump -U postgres academy > academy.sql
```

`-Fc` (custom) paling fleksibel karena `pg_restore` bisa memilih tabel tertentu dan memakai parallel restore.

## Restore

```bash
createdb academy_baru
pg_restore -U postgres -d academy_baru academy.dump
pg_restore -U postgres -d academy_baru -t produk academy.dump
```

Restore ke database baru lebih aman daripada menimpa langsung.

## Backup Fisik dan PITR

```bash
pg_basebackup -D /backup/base -Ft -z -X stream
```

Untuk PITR, siapkan `restore_command` yang mengambil WAL dari arsip, lalu buat `recovery.signal` dengan target waktu:

```text
restore_command = 'cp /arsip/wal/%f %p'
recovery_target_time = '2026-11-20 08:00:00+07'
```

## Arsip WAL

```text
archive_mode = on
archive_command = 'cp %p /arsip/wal/%f'
```

WAL yang terarsip memungkinkan memulihkan database sampai detik sebelum insiden.

## Strategi 3-2-1

3 salinan, 2 media berbeda, 1 lokasi terpisah. Simpan kunci enkripsi terpisah dari backup.

<div class="note">💡 `pg_dump` saat ada transaksi panjang bisa memakan waktu lama karena harus melihat snapshot konsisten. Pantau durasi dan jadwalkan di luar jam sibuk.</div>

## Di Dunia Nyata

- **Development**: dump harian untuk replikasi data ke lokal (tanpa data sensitif).
- **Produksi**: base backup harian + WAL continuous.
- **Migrasi**: dump/restore untuk pindah versi mayor.
- **Insiden**: PITR mengembalikan sebelum DELETE salah.
