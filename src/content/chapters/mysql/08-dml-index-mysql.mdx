DML mengubah isi tabel; index mempercepat cara data itu ditemukan. Keduanya berhubungan: semakin banyak index, pembacaan tertentu makin cepat tetapi setiap penulisan makin mahal.

## 3 Perintah DML Tulis

| Perintah | Fungsi | Risiko | Pengaman |
|----------|--------|--------|----------|
| `INSERT` | tambah baris | tipe/constraint salah | sebut daftar kolom |
| `UPDATE` | ubah baris | semua baris berubah | uji WHERE dengan SELECT |
| `DELETE` | hapus baris | kehilangan data | transaksi + backup |

```sql
INSERT INTO karyawan (nama, jabatan, gaji, dept)
VALUES
  ('Tono Wijaya', 'Mobile Developer', 9800000, 'Engineering'),
  ('Nina Sari', 'Data Engineer', 10200000, 'Data');
```

Satu INSERT multi-baris mengurangi perjalanan jaringan dan overhead parsing. Untuk data sangat besar gunakan mekanisme bulk load MySQL dengan validasi dan staging table.

## Pola Aman UPDATE dan DELETE

```sql
START TRANSACTION;
SELECT id, nama, gaji FROM karyawan WHERE dept = 'Design' FOR UPDATE;
UPDATE karyawan SET gaji = gaji + 500000 WHERE dept = 'Design';
-- cocokkan ROW_COUNT() dan hasil SELECT
COMMIT;
```

Empat langkah aman: mulai transaksi, SELECT target, lakukan perubahan, COMMIT bila jumlah baris sesuai — atau ROLLBACK bila tidak. Jangan menganggap `sql_safe_updates` sebagai satu-satunya pengaman; kondisi berindex pun bisa tetap terlalu luas.

## 3 Struktur Index Utama

| Struktur | Cocok untuk | Contoh |
|----------|-------------|--------|
| B-tree | kesamaan, rentang, urutan, prefix | `WHERE dept = ? ORDER BY gaji` |
| FULLTEXT | pencarian kata dalam teks | `MATCH(isi) AGAINST(...)` |
| Spatial (R-tree) | geometri/lokasi | area yang memuat titik |

InnoDB memakai B-tree untuk primary dan secondary index. Hash index internal dapat muncul sebagai optimasi adaptif, tetapi bukan index umum yang kamu desain untuk tabel InnoDB.

## Index Tunggal dan Komposit

```sql
CREATE INDEX idx_karyawan_dept_gaji ON karyawan (dept, gaji);
```

Index komposit mengikuti aturan **leftmost prefix**. `(dept, gaji)` membantu:

1. `WHERE dept = 'Data'`;
2. `WHERE dept = 'Data' AND gaji >= 9000000`;
3. urutan gaji dalam satu dept.

Ia tidak optimal untuk `WHERE gaji >= 9000000` tanpa dept. Urutkan kolom berdasarkan pola query nyata: equality biasanya sebelum range.

## Clustered dan Secondary Index InnoDB

Primary key adalah clustered index: baris tabel disimpan mengikuti struktur primary key. Secondary index menyimpan nilainya plus primary key untuk menemukan baris penuh. Karena itu primary key yang pendek dan stabil menghemat semua secondary index; `BIGINT` biasanya lebih hemat daripada string UUID acak yang panjang.

## EXPLAIN dan Selectivity

```sql
EXPLAIN SELECT nama, gaji
FROM karyawan
WHERE dept = 'Data'
ORDER BY gaji DESC;
```

Baca tiga kolom utama: `type` (ALL = full scan; ref/range lebih selektif), `key` (index dipilih), `rows` (perkiraan baris dibaca). Index kolom dengan sedikit nilai seperti boolean sering tidak membantu sendiri karena terlalu banyak baris tetap cocok.

## Biaya Index

Setiap index memakai disk dan harus diperbarui saat INSERT/UPDATE/DELETE. Hindari membuat index untuk setiap kolom. Gunakan *slow query log* dan EXPLAIN untuk menemukan query nyata, lalu desain index yang melayani filter, JOIN, dan urutannya.

## Di Dunia Nyata

- Login: UNIQUE index pada email mempercepat lookup sekaligus mencegah akun ganda.
- Riwayat pesanan: index `(user_id, created_at)` melayani daftar terbaru per pengguna.
- Katalog: FULLTEXT untuk pencarian deskripsi, bukan `LIKE '%kata%'` pada jutaan baris.
- Maintenance: hapus index duplikat setelah memastikan tidak dipakai constraint/query.
