Strategi branch mengatur **kapan dan bagaimana** perubahan bubar masuk ke kode utama. Tidak ada satu pola yang cocok untuk semua tim.

## Git Flow

```text
main        ----o---------o------rilis
                 \       /
develop     --o---o---o---o---
                \   /
feature/x    ----o---
```

| Branch | Fungsi | Umur |
|---|---|---|
| main | kode produksi | permanen |
| develop | integrasi fitur | permanen |
| feature/* | mengerjakan satu fitur | singkat |
| release/* | stabilisasi rilis | sedang |
| hotfix/* | perbaikan darurat produksi | singkat |

## Trunk-Based

Pengembang membuat branch kecil, merge ke `main` dalam hitungan jam atau hari, dan menjaga kode selalu bisa di-deploy. Fitur besar disembunyikan dengan feature flag.

```bash
git switch -c feature/keranjang
# beberapa commit kecil
git fetch origin
git rebase origin/main
git push origin feature/keranjang
```

## Perbandingan

| Aspek | Git Flow | Trunk-based |
|---|---|---|
| Jumlah branch | lebih banyak | sedikit |
| Frekuensi merge | lebih jarang |非常 sering |
| Cocok untuk | rilis terjadwal | continuous delivery |
| Kompleksitas | sedang | rendah |

<div class="note">💡 Aturan paling penting bukan nama polanya, melainkan disiplin: branch harus punya tujuan jelas dan segera selesai.</div>

## Konvensi Penamaan

```text
feature/ringkas-teks
fix/bug-tanggal
chore/perbarui-dependensi
docs/panduan-deploy
refactor/rapi-parser
```

Awalan memudahkan filter dan otomatisasi changelog. Hindari nama seperti `test`, `coba`, atau `final2`.
