**Cherry-pick** mengambil satu commit dari branch lain dan menerapkannya ke HEAD saat ini. Bayangkan memilih satu buah dari pohon tanpa memetik seluruh cabangnya.

## Alur Dasar

```bash
git log --oneline fitur/perbaikan   # cari hash commit
git switch main
git cherry-pick a1b2c3d
git log --oneline -3
```

Commit baru dibuat dengan pesan yang sama, tetapi hash berbeda.

## Opsi Penting

| Opsi | Fungsi |
|---|---|
| `-n`, `--no-commit` | terapkan patch tanpa commit |
| `-x` | tambahkan baris "(cherry picked from ...)" |
| `--edit` | sunting pesan commit |
| `--abort` | batalkan proses saat konflik |
| `--continue` | lanjutkan setelah konflik selesai |

## Kasus Backport

```text
main        --o--o--F--o      F = fix keamanan
release/1.4 --o--o--------F'  F' = cherry-pick dari F
```

Perbaikan masuk ke rilis lama tanpa membawa fitur baru dari `main`.

## Risiko

- Patch bisa bergantung pada commit sebelumnya, sehingga cherry-pick tunggal gagal atau tidak lengkap.
- Duplikasi perubahan membuat riwayat sulit dibaca bila dilakukan berlebihan.
- Konflik tetap harus diselesaikan manual.

<div class="note">💡 Bila seluruh rangkaian commit dibutuhkan, pertimbangkan `git rebase` atau `git merge` daripada cherry-pick berkali-kali.</div>

## Praktik Baik

- Selalu sertakan `-x` saat backport agar asal commit tercatat.
- Uji hasilnya — patch yang sama belum tentu benar di konteks branch berbeda.
- Simpan catatan rilis yang menyebut commit asli dan commit hasil cherry-pick.
