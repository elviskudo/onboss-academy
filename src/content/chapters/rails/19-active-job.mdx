## Kenapa Background Job

```ruby
class LaporanJob < ApplicationJob
  queue_as :default

  def perform(user_id)
    user = User.find(user_id)
    Laporan.generate(user)
  end
end

LaporanJob.perform_later(current_user.id)
LaporanJob.set(wait: 5.minutes).perform_later(current_user.id)
```

Request web sebaiknya selesai dalam ratusan milidetik. Mengirim email, membuat PDF, atau memproses video di dalam request membuat pengguna menunggu dan server kehabisan thread.

```ruby
class LaporanJob < ApplicationJob
  def perform(user_id)
    user = User.find(user_id)
    Laporan.generate(user)
  end
end
```

Simpan **ID**, bukan objek Active Record, sebagai argumen. Objek bisa berubah atau hilang sebelum job dijalankan.

## Adapter

| Adapter | Kekuatan | Catatan |
|---|---|---|
| `async` | tanpa setup | hanya in-process, hilang saat restart |
| `sidekiq` | cepat, populer | butuh Redis |
| `resque` | sederhana | butuh Redis |
| `delayed_job` | berbasis database | tanpa servis tambahan |

Di produksi, ganti adapter di `config/application.rb` lewat `config.active_job.queue_adapter = :sidekiq`.

## Otomatisasi Retry

```ruby
class WebhookJob < ApplicationJob
  retry_on Timeout::Error, wait: :polynomially_longer, attempts: 5
  discard_on ActiveRecord::RecordNotFound
end
```

`retry_on` mengulang saat error sementara; `discard_on` membuang job saat error permanen.

## Job dan Transaksi

Job yang diantre di dalam transaksi database bisa dijalankan sebelum transaksi commit. Gunakan `after_commit` untuk menjamin data sudah tersimpan:

```ruby
after_commit -> { LaporanJob.perform_later(id) }, on: :create
```

<div class="note">💡 Job harus idempoten — menjalankannya dua kali boleh menghasilkan efek yang sama. Antrean modern kadang mengirim ulang job saat worker crash.</div>
