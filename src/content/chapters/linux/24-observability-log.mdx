Ketika sistem bermasalah, pertanyaan pertama selalu: **apa yang berubah?** Observability membantu menjawabnya dengan bukti, bukan tebakan.

## Tiga Sinyal

| Sinyal | Bentuk | Pertanyaan |
|---|---|---|
| Log | event diskrit | apa yang terjadi? |
| Metrik | angka time-series | seberapa sering/berapa lama? |
| Trace | jejak permintaan | di mana lambatnya? |

## journalctl

```bash
journalctl -u nginx -n 50 --no-pager
journalctl -u nginx -f
journalctl --since "1 hour ago"
journalctl -p err -b
```

```bash
journalctl _PID=1234
journalctl -o json-pretty
```

## Log File

```bash
tail -f /var/log/syslog
grep -i "failed" /var/log/auth.log
zcat /var/log/nginx/access.log.1.gz | head
```

Rotasi log diatur oleh `logrotate`:

```text
/var/log/nginx/*.log {
    daily
    rotate 14
    compress
    missingok
}
```

## Metrik Sederhana

```bash
uptime
free -h
mpstat 1 5
iostat -x 1
ss -s
```

Untuk skala besar, metrik dikirim ke Prometheus/Grafana. Prinsipnya tetap sama: kumpulkan angka yang bisa dibandingkan dari waktu ke waktu.

<div class="note">💡 Jangan hanya mengumpulkan data. Tentukan dulu pertanyaan yang ingin dijawab dan ambang alert yang benar-benar bermakna.</div>

## Praktik Baik

- Gunakan timestamp konsisten (UTC disarankan).
- Sertakan request ID agar log bisa dirangkai.
- Hindari mencatat kata sandi atau token.
- Uji alert secara berkala supaya tidak usang.
