Sesi menyimpan status login. Karena cookie dikirim otomatis, penyerang bisa "menumpang" pada sesi korban lewat permintaan lintas situs.

## Anatomi Cookie Aman

```http
Set-Cookie: sid=...; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

| Atribut | Fungsi |
|---|---|
| `HttpOnly` | JavaScript tidak bisa membaca |
| `Secure` | Hanya dikirim lewat HTTPS |
| `SameSite` | Batasi pengiriman lintas situs |
| `Max-Age` / `Expires` | Masa hidup jelas |
| `Path` | Batasi cakupan URL |

## Token CSRF

```text
server buat token acak -> simpan di sesi -> sisipkan ke form
saat POST -> bandingkan token form dengan token sesi
```

Gunakan perbandingan konstan-waktu untuk mencegah serangan timing. Token tidak boleh muncul di log atau URL karena URL tersimpan di riwayat dan referer.

## Daur Hidup Sesi

1. **Sebelum login** — sesi sementara.
2. **Saat login sukses** — regenerasi ID sesi.
3. **Aktif** — perbarui aktivitas, tetapkan batas diam.
4. **Logout** — hapus di server **dan** di browser.
5. **Kedaluwarsa** — paksa login ulang untuk operasi sensitif.

## Double Submit dan Header Kustom

Pola lain: kirim token di cookie dan di header `X-CSRF-Token`, lalu bandingkan. Karena penyerang lintas situs tidak bisa membaca atau menetapkan header kustom tanpa CORS, permintaannya gagal.

<div class="note">💡 Jangan simpan token akses di `localStorage` bila bisa dihindari—XSS langsung bisa membacanya. Cookie `HttpOnly` dengan CSRF token lebih sulit dicuri.</div>
