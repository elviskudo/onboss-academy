Sebuah image bisa memiliki banyak **tag**. Tag bukan versi di dalam image—ia hanya label yang menunjuk ke ID. Memahami ini penting agar pipeline deploy tidak berubah diam-diam.

## Anatomi Nama Image

```text
registry.example.com/tim/aplikasi:1.4.2
└── registry         └── repository  └── tag
```

| Bagian | Contoh | Catatan |
|---|---|---|
| Registry | `docker.io`, `ghcr.io` | Default `docker.io` bila dihilangkan |
| Repository | `tim/aplikasi` | Boleh bertingkat |
| Tag | `1.4.2`, `alpine`, `latest` | Bebas, tapi gunakan konvensi yang jelas |

## Membuat dan Memindahkan Tag

```bash
docker build -t aplikasi:1.4.2 .
docker tag aplikasi:1.4.2 aplikasi:latest
docker tag aplikasi:1.4.2 registry.internal/tim/aplikasi:1.4.2
docker push registry.internal/tim/aplikasi:1.4.2
```

`docker tag` tidak membuat salinan data—hanya menambah nama lain untuk layer yang sama.

## Masalah `latest`

`latest` adalah tag biasa yang diberikan docker saat tidak ada tag disebut. Maintainers bisa menggesernya kapan saja. Dua server yang menarik image pada hari berbeda bisa menjalankan kode berbeda walaupun perintahnya sama.

Solusinya: pakai nomor versi semantik (`1.4.2`) untuk rilis, atau digest untuk jaminan paling kuat:

```bash
docker pull nginx@sha256:2f5e...
```

## Strategi Tag yang Sehat

1. **Versi rilis** — `1.4.2` untuk build yang sudah diuji.
2. **Tag bendungan** — `1.4` dan `1` mengikuti patch terbaru dalam kanal yang sama.
3. **Tag komit** — `sha-&lt;7 karakter>` untuk traceability ke git.
4. **Tag lingkungan** — `staging`, `prod`, dikelola oleh pipeline, bukan manual.

```bash
docker images aplikasi --format '{{.Tag}}\t{{.ID}}\t{{.CreatedSince}}'
docker rmi aplikasi:latest   # hapus alias, image asal tetap ada bila tag lain masih ada
```

<div class="note">💡 Image baru dihapus hanya setelah tag terakhir yang menunjuk kepadanya dihapus dan tidak ada container yang memakainya.</div>
