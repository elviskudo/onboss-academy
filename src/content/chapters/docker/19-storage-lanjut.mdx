Container bersifat ephemeral: data di layer writable hilang saat container dihapus. Tiga mekanisme berikut memberi pilihan penyimpanan yang persisten maupun sementara.

## Tiga Jenis Mount

| Jenis | Sumber | Hilang saat stop? | Cocok untuk |
|---|---|---|---|
| Volume bernama | dikelola Docker | Tidak | Database, data aplikasi |
| Bind mount | path di host | Tidak | Kode saat development, config host |
| tmpfs | RAM | Ya | Cache, file sensitif sementara |

## Contoh Praktis

```bash
docker volume create data-app

docker run -d --name db \
  -v data-app:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=rahasia \
  postgres:16-alpine

docker run --rm -v "$PWD/config:/etc/app:ro" app:1.0
docker run --rm --tmpfs /cache:size=64m app:1.0
```

## Volume Saat Build vs Run

```dockerfile
VOLUME /var/lib/app
```

Instruksi `VOLUME` mendeklarasikan titik mount, tetapi **tidak** mengisi data dari image ke volume kosong secara otomatis... kecuali Docker menyalin isi direktori tersebut saat volume pertama dibuat. Tetap lebih jelas bila mount ditentukan di `docker run` atau Compose.

## Backup dan Migrasi

```bash
docker run --rm -v data-app:/data -v "$PWD:/backup" \
  alpine tar czf /backup/data.tar.gz -C /data .

docker run --rm -v data-app:/data -v "$PWD:/backup" \
  alpine tar xzf /backup/data.tar.gz -C /data
```

Pola "container sementara untuk backup" menghindari kebutuhan menginstal tool di image produksi.

## Jebakan Umum

- Bind mount menimpa isi folder di image—file yang sudah ada jadi tidak terlihat.
- Hak akses (UID/GID) harus cocok antara host dan proses di container.
- `docker compose down -v` menghapus volume bernama, termasuk datanya.

<div class="note">💡 Untuk database, lebih aman memakai named volume daripada bind mount: Docker mengelola izin dan lokasi penyimpanan tanpa bergantung pada struktur folder host.</div>
