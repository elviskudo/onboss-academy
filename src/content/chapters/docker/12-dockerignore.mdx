`.dockerignore` bekerja seperti `.gitignore`, tetapi diskonsultasi **sebelum** build context dikirim ke daemon. File yang terfilter tidak bisa diakses oleh perintah `COPY` maupun `ADD`.

## Contoh Minimal

```dockerignore
.git
.github
node_modules
__pycache__
*.pyc
.env
.env.*
*.log
Dockerfile
docker-compose*.yml
README.md
```

Meletakkan `Dockerfile` sendiri di ignore list aman: Docker tetap membacanya secara terpisah, hanya tidak menyalinnya ke dalam image bila ada `COPY . .`.

## Pola dan Negasi

| Pola | Arti |
|---|---|
| `*.log` | Semua berkas berakhir `.log` di semua level |
| `/temp/*` | Hanya di root context |
| `data/**` | Seluruh isi folder data |
| `!config/contoh.env` | Sertakan kembali satu file |
| `**/.DS_Store` | File sistem di folder mana pun |

Urutan penting: aturan terakhir yang cocok yang menang.

## File Sensitif

```dockerignore
.env
.env.production
*.pem
id_rsa
credentials.json
```

Ini **bukan pengganti** secret manager. File yang sudah masuk layer tidak bisa dihapus dengan aman hanya dengan `rm` di layer berikutnya—riwayat layer tetap menyimpannya. Gunakan BuildKit secret mount untuk data saat build.

## Dampak pada Cache

Context yang kecil membuat hash cache lebih stabil. Misalnya, perubahan di `README.md` tidak membatalkan cache layer `RUN npm install` bila README sudah dikecualikan. Sebaliknya, menyalin seluruh folder proyek membuat perubahan kecil pada file apa pun membatalkan hampir semua layer berikutnya.

<div class="note">💡 Jalankan `docker build` dari folder sedekat mungkin dengan Dockerfile. Semakin luas context, semakin banyak data yang perlu dikirim—bahkan yang akhirnya diabaikan.</div>
