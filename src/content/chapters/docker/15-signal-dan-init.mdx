Saat `docker stop` dipanggil, daemon mengirim **SIGTERM** ke PID 1 di dalam container, menunggu beberapa detik, lalu **SIGKILL** bila proses belum keluar. Shutdown yang rapi memberi aplikasi waktu menutup koneksi dan menyelesaikan pekerjaan.

## Mengapa PID 1 Istimewa

 PID 1 adalah **init**. Ia menerima sinyal langsung dari kernel dan bertugas meneruskannya ke proses anak. Banyak aplikasi tidak dirancang sebagai init: `node server.js` atau `sh -c ...` kerap mengabaikan SIGTERM, sehingga Docker terpaksa membunuhnya dengan SIGKILL.

## Solusi 1: `--init`

```bash
docker run --init -d --name app app:1.0
```

Docker menyisipkan init ringan (turunan tini) yang meneruskan sinyal dan memanen proses zombie. Ini jalan tercepat tanpa mengubah image.

## Solusi 2: tini di Dockerfile

```dockerfile
FROM node:20-alpine
RUN apk add --no-cache tini
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "server.js"]
```

`--` penting agar tini berhenti mem-parsing argumen dan meneruskan sisanya ke aplikasi.

## Mengatur Sinyal dan Timeout

```dockerfile
STOPSIGNAL SIGQUIT
```

```bash
docker stop --time 30 app     # tunggu 30 detik sebelum SIGKILL
docker kill --signal SIGINT app
```

## Tanda Shutdown Bermasalah

- Log berisi `SIGTERM received` tetapi tidak ada `server closed`.
- Request yang sedang berjalan terputus saat deploy.
- Muncul proses `<defunct>` di `docker top`.

<div class="note">💡 Di Kubernetes, `terminationGracePeriodSeconds` harus lebih besar dari waktu yang dibutuhkan aplikasi untuk shutdown. Sinkronkan dengan `docker stop --time` saat menguji lokal.</div>
