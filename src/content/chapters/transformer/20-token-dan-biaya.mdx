Setiap permintaan ke LLM mengonsumsi **token**. Memahaminya membantu menjaga jawaban tetap utuh dan tagihan tetap terkendali.

## Anatomi Permintaan

```text
system prompt + riwayat + dokumen + pertanyaan + jawaban <= jendela konteks
```

```python
konteks = 128_000
input_token = 118_000
output_token = 2_000
sisa = konteks - input_token - output_token
print("sisa:", sisa)
```

Kalau `output_token` melebihi sisa, jawaban terpotong di tengah kalimat.

## Strategi Efisien

| Teknik | Efek |
|---|---|
| Ringkas riwayat | mengurangi token berulang |
| Retrieval selektif | hanya kirim potongan relevan |
| System prompt singkat | menghemat setiap permintaan |
| Batasi `max_tokens` | mencegah output berlebih |
| Cache prompt | menghemat token identik berulang |

## KV Cache

Saat generate, model menyimpan **Key** dan **Value** tiap layer untuk token sebelumnya. Ini mempercepat decoding, tetapi mengonsumsi memori GPU yang tumbuh seiring panjang konteks.

```text
memori KV ≈ 2 × layer × token × head × d_head × bytes
```

<div class="note">💡 “Konteks 128K” bukan berarti model selalu memperhatikan semua token dengan baik. Informasi di tengah dokumen sangat panjang kadang kurang terpakai — tetap susun dokumen penting di awal atau akhir.</div>

## Praktik Produksi

- Catat jumlah token tiap permintaan di log observability.
- Beri peringatan saat percakapan mendekati batas konteks.
- Uji panjang prompt yang realistis, bukan hanya contoh pendek.
- Pisahkan permintaan besar menjadi beberapa panggilan bila memungkinkan.
