## Prompt Engineering

```python
prompt = """
Peran: asisten dukungan pelanggan toko buku.
Konteks: kebijakan return 14 hari sejak tanggal terima, belum termasuk ongkir.
Aturan: jawab maksimal 3 kalimat, sopan, bahasa Indonesia.
Pertanyaan pelanggan: "Bisa return buku yang sudah dibuka?"
"""
print(prompt)
```

Ada **4 elemen prompt praktis**:

| Elemen | Fungsi | Contoh |
|--------|--------|--------|
| Peran | menetapkan sudut pandang | “asisten dukungan” |
| Konteks | memberi fakta relevan | kebijakan return |
| Tugas | menjelaskan pekerjaan | jawab pertanyaan |
| Format | membatasi bentuk hasil | maksimal 3 kalimat |

Contoh input-output (**few-shot**) dapat menambah konsistensi untuk format yang sulit dijelaskan, tetapi juga menambah token dan biaya.

## RAG: Menyuntik Dokumen

```
Pertanyaan user
   -> cari dokumen relevan (pencarian vektor/kata)
   -> sisipkan dokumen ke prompt
   -> LLM menjawab berdasarkan dokumen tersebut
   -> sertakan kutipan sumber
```

RAG membuat jawaban berpijak pada dokumen organisasi — tanpa melatih ulang model.

## 5 Tahap Pipeline RAG

| Tahap | Fungsi |
|-------|--------|
| Ingest | mengambil dokumen sumber |
| Chunk | memotong dokumen menjadi bagian |
| Index | menyimpan embedding/kata kunci |
| Retrieve | mencari chunk relevan untuk pertanyaan |
| Generate | menjawab memakai chunk dan memberi sumber |

Kualitas RAG bergantung pada retrieval. Jika chunk yang benar tidak ditemukan, LLM tidak punya fakta yang diperlukan. Evaluasi retrieval (apakah sumber benar masuk) terpisah dari evaluasi jawaban.

## Fine-Tuning vs Prompt vs RAG

| Pendekatan | Mengubah apa | Cocok ketika | Biaya relatif |
|------------|--------------|--------------|---------------|
| Prompt | instruksi per permintaan | tugas dan konteks sederhana | rendah |
| RAG | konteks dari dokumen | fakta privat/sering diperbarui | sedang |
| Fine-tuning | bobot/perilaku model | gaya/format berulang | tinggi |

Mulailah dari yang paling murah: prompt dulu, lalu RAG, baru fine-tuning bila memang diperlukan. Fine-tuning bukan database fakta: memperbarui satu kebijakan lewat dokumen RAG jauh lebih mudah daripada melatih ulang model.

## Keamanan dan Etika

- **Jangan kirim** data pribadi/kredensial ke layaran pihak ketiga tanpa dasar yang jelas.
- **Risiko prompt injection** — instruksi jahat bisa tersembunyi dalam dokumen yang dibaca model; perlakukan konten eksternal sebagai data, bukan instruksi.
- **Simpan log** prompt dan output untuk audit, khususnya di bidang ter-regulasi.

## Monitoring Setelah Rilis

```python
# Sketsa ringkas kualitas layanan
metrik = {
    "ulasan_negatif_per_minggu": 12,
    "timeout_rate": 0.02,
    "halusinasi_terlapor": 3,
}
if metrik["halusinasi_terlapor"] > 0:
    print("Perlu evaluasi sumber RAG dan instruksi sistem")
```

Pantau keluhan pengguna, keterlambatan, dan kasus halusinasi — lalu perbaiki sumber daya (dokumen, prompt, atau model). Sedikitnya ukur 4 hal: kualitas jawaban, ketepatan sumber, latensi, dan biaya per permintaan.

## Di Dunia Nyata

- **FAQ kebijakan perusahaan** — RAG mengambil aturan terbaru dan mencantumkan dokumen sumber.
- **Ekstraksi invoice** — prompt menetapkan schema JSON; validator menolak keluaran yang tidak sesuai.
- **Asisten support** — fine-tuning dipertimbangkan bila ribuan jawaban harus konsisten dalam nada dan format.
- **Pencarian manual teknis** — retrieval memilih bagian manual yang relevan sebelum LLM merangkum langkah.
- **Aplikasi legal internal** — izin dokumen diperiksa sebelum retrieval agar pengguna tidak melihat data terlarang.

<div class="note">💡 Jalur paling hemat dalam praktik: prompt yang jelas -> RAG bila butuh dokumen -> fine-tuning hanya untuk pola yang tidak bisa dicapai keduanya.</div>
